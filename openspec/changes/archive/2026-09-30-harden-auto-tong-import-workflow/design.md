# Design

## Context

문제의 배경과 범위는 [proposal.md](proposal.md), 상세 근거는 [점검 보고서](../../../reviews/2026-09-30/code-review.md)를 따른다. 수정 전 `watcher.rs`는 스캔, 설치, Java 준비, 이력 기록, 알림을 순차 실행했다. 설치 함수는 실제 인스턴스에 직접 썼고, `tracker.rs`는 성공과 실패를 별도 map으로 저장했다. 진행 이벤트에는 파일명·백분율·문자열 상태만 있었다.

여러 저장 장치에 대한 원자적 트랜잭션은 제공되지 않는다. Windows의 파일 잠금과 junction, Prism의 설정 캐시, 동기화 폴더의 쓰기 진행 상태를 고려해야 한다. 아래 구조는 제안이며 아직 구현하지 않았다.

## Goals / Non-Goals

**Goals:**

- 오류를 단계별로 복구하고 원본·인스턴스·이력의 연결을 일관되게 유지한다.
- 설정과 취소 처리를 다운로드 수명에서 분리한다.
- 파일 시스템, HTTP, 프로세스 조회, 시계를 대체할 수 있는 경계를 만들어 실제 사용자 환경을 건드리지 않고 장애를 검증한다.

**Non-Goals:**

- 분산 작업 큐, DB 서버, UI 프레임워크 도입.
- 모든 버전의 Minecraft와 모든 운영체제에 대한 검증 완료 선언.
- 이력 초기화, 사용자 인스턴스 일괄 삭제 또는 보안 기능 비활성화로 오류 우회.

## Decisions

### D1. 모든 파일 쓰기는 공통 경로 정책을 통과한다 — R01, R20

`import_path` 모듈에 Windows 경로 component 검증을 둔다. 구분자 정규화 후 부모·루트·prefix, UNC·장치 경로, 콜론, 예약 이름, 끝의 점·공백과 정규화 후 중복 경로를 거부한다. 입력 인코딩은 기존 ZIP 이름 디코딩을 유지한다. 생성할 디렉터리의 기존 상위 경로에 링크·reparse point가 있는지도 검사한다. staging 디렉터리는 앱이 고유하게 만들고 링크를 추출하지 않는다. 쓰기 직전 경로 검증과 no-follow 성격의 열기 정책을 함께 사용하여 검사 후 경로가 바뀌는 경우를 다룬다.

공통 preflight가 ZIP 형식, MRPACK `formatVersion=1`, `game=minecraft`, Minecraft 의존성, 해시·URL 및 지원 로더를 검증한다. 알 수 없는 실행 필수 의존성을 조용히 버리지 않는다. 패키지 파일 수, 단일 크기, 총 해제량 상한은 한 정책으로 관리하고 초과 이유를 표시한다.

검토한 대안: 각 importer에 문자열 검사를 추가하는 방식은 Windows rooted 경로 문제를 반복하므로 공통화한다. `canonicalize`만 사용하는 방식은 아직 없는 출력 파일을 처리할 수 없어 component 검사와 상위 경로 확인을 함께 사용한다.

### D2. 파일 준비와 설치 확정을 분리한다 — R02–R05, R14, R15

`ImportPlan`에 원본 식별자, 대상, 형식, 기대 파일·해시, 적용 순서를 저장한다. HTTP는 응답을 스트리밍하며 SHA-512와 크기를 검증하고 `.part`를 완료 파일로 승격한다. 기존 캐시도 해시 검증 후 복사한다. URL 후보를 순서대로 시도하되 제한된 재시도·backoff를 사용하고 마지막 실패 이유를 보존한다. 운영 다운로드는 유효한 HTTPS로 제한하고 리다이렉트에도 정책을 적용한다. loopback HTTP 허용은 테스트 전용 transport로 한정한다.

초기 제안값은 연결 10초, 데이터 유휴 30초, 파일 전체 15분, URL별 최대 3회 시도다. 상한은 주입 가능한 정책으로 두고 대형 팩 검증 후 문서화한다. 메모리에 전체 ZIP·응답을 올리지 않으며 CPU·동기 파일 작업은 제어 루프 밖에서 수행한다.

적용 순서는 다운로드 → `overrides` → `client-overrides`다. 클라이언트 `unsupported`는 제외하고 `optional`은 기존 동작과 호환되도록 기본 포함한다. 선택한 파일은 모두 성공 조건에 포함한다. 전용 선택 UI는 이번 범위에 추가하지 않는다.

기존 인스턴스 업데이트는 다음 절차를 사용한다.

1. 같은 볼륨의 Prism 자동 검색 대상 밖에 고유 staging/backup 디렉터리를 만든다.
2. 기존 설치와 파일 소유 기록을 확인한다. 월드·스크린샷·옵션 및 관리하지 않는 파일을 보존한다. 기존 파일을 쓸 수 있는 hardlink로 공유하지 않는다.
3. 이전 설치가 관리했던 파일 중 수정되지 않은 파일만 교체·제거한다. 사용자가 수정한 파일과 충돌하면 자동 확정을 보류한다. 이전 소유 기록이 없으면 알 수 없는 파일을 삭제하지 않는다.
4. 새 콘텐츠, 메타데이터, Java를 staging에서 검증한다.
5. 런처·게임 상태를 재확인한 뒤 commit journal을 저장한다. 기존 디렉터리를 backup으로 이동하고 staging을 최종 위치로 이동한다.
6. 이력을 저장하고 성공 이벤트를 보낸다. 복구에 필요한 backup은 이력 저장 확인 전 삭제하지 않는다.

두 번의 rename을 하나의 원자적 교체라고 가정하지 않는다. journal에 `prepared`, `backup-moved`, `installed`, `recorded`와 실제 경로·작업 ID를 남기고 각 단계 중단을 복구한다. 이력 저장 실패 시 새 설치와 journal을 보존한 `recovery-required` 상태로 멈추며 후속 덮어쓰기를 막는다. 기존 backup을 복구할지 검증된 새 설치 이력을 완성할지는 journal 단계와 파일 검증으로 결정한다.

검토한 대안: 직접 덮어쓰기는 실패 전 변경을 복구할 수 없다. 전체 삭제 후 재설치는 사용자 데이터를 잃는다. staging은 추가 용량이 필요하지만 설치 실패를 기존 인스턴스와 분리한다.

### D3. 명령 처리와 작업 실행을 분리한다 — R05–R08, R15

제어 루프는 설정·취소·재시도를 처리하고 bounded worker에 작업을 전달한다. 스캔 신호만 debounce/coalesce하며 typed 제어 명령은 비우지 않는다. 설정은 `config_revision`으로 저장·적용·감시 등록 결과를 확인한다. 작업은 시작 시 설정 snapshot을 갖고, 이전 설정 작업은 취소 또는 안전한 준비 단계 종료 후 최신 설정으로 재계획한다. 이미 확정 중인 작업의 목적지를 도중에 바꾸지 않는다.

감시 객체의 수명을 제어 루프가 관리해 폴더 변경 즉시 unwatch/watch한다. 감시 실패는 표시하고 polling으로 대체한다. 태그 정규화 결과가 비어 있으면 저장을 거부한다.

`source_id`는 정규화된 절대 감시 루트와 상대 경로에서 만든다. Windows 경로의 대소문자·구분자 차이를 정규화한다. 대상 폴더는 표시용 이름과 안정적인 식별자 suffix로 구분하며 기존 매핑을 재사용한다. 수정 시간 정밀도·크기와 내용 해시를 기록한다. 이벤트가 없는 동기화 변경도 찾도록 주기적인 내용 검증을 수행한다. 안정화 관찰 후 임시 원본 snapshot을 만들고 복사 전후 fingerprint를 비교한다.

동일 source/target의 설치는 직렬화한다. 재가져오기는 `Retry/ReplaceManaged` 의도를 가진 새 작업이며 성공 이력을 먼저 삭제하지 않는다. 네트워크·잠금 실패는 제한된 자동 재시도 대상, 형식·경로 오류는 원본 수정 또는 수동 조치 대상으로 분류한다.

검토한 대안: 현재 channel drain에 예외만 추가하는 수정은 다운로드 중 제어 처리가 막히는 문제를 남긴다. 제어 루프와 worker를 나누되 초기 worker 동시성은 1로 유지해 변경 범위를 제한한다.

### D4. 이력을 하나의 직렬 저장 경로로 관리한다 — R08, R09

JSON 저장을 유지하고 다음 개념을 가진 versioned schema를 도입한다.

- `schema_version`, `source_id`, `source_root`, `relative_path`, `instance_id`.
- `installed`: 마지막 확정 fingerprint·버전·시각·관리 파일 목록.
- `last_attempt`: `job_id`, 단계, 오류 분류, 재시도 가능 여부, 시각.
- `config_revision`, 복구 중인 journal 연결 정보.

한 원본의 현재 상태는 한 항목이며 설치된 버전과 최근 실패를 함께 표현한다. 저장 담당이 상태 복제 → 변경 → 고유 임시 파일 쓰기·flush → 대상 교체 → 메모리 공개를 직렬 수행한다. 이 순서 안에 다른 저장이 끼어들지 않는다. 실패 시 마지막 정상 메모리를 유지한다. 읽기 실패를 빈 정상 데이터로 바꾸지 않는다.

검토한 대안: SQLite는 강한 트랜잭션을 제공하지만 현 규모에서는 의존성과 이전 비용이 있다. JSON을 유지하되 설치 journal은 별도로 두어 디렉터리 변경과 이력 변경 사이를 복구한다. 파일·디렉터리 flush와 Windows 교체 동작은 fault injection 및 실제 NTFS에서 확인한다.

### D5. 선택한 런처와 실행 환경을 명시적으로 연결한다 — R10–R13, R21

`LauncherTarget`에 실행 파일과 검증된 데이터 디렉터리를 함께 저장한다. portable 표식·실행 설정 등 결정적인 근거를 먼저 사용하고, 모호하면 데이터 위치를 명시적으로 선택하도록 한다. 기본 폴더가 있다는 이유로 사용자의 portable 선택을 바꾸지 않는다.

로더 component 생성은 공통 매핑으로 통합한다. NeoForge UID는 `net.neoforged`다. [Prism 공식 component 목록](https://raw.githubusercontent.com/PrismLauncher/meta-launcher/master/net.neoforged/index.json)을 기준 fixture로 남긴다.

Java 요구사항은 버전별 공식 런처 메타데이터를 해석하고 검증된 결과를 캐시한다. 알려진 구버전은 검증된 fallback 표를 사용할 수 있으나 모르는 버전은 추정하지 않는다. Minecraft 26.1은 Java 25를 요구한다. [Prism 공식 Minecraft 26.1 메타데이터](https://raw.githubusercontent.com/PrismLauncher/meta-launcher/master/net.minecraft/26.1.json).

Java 설치는 checksum이 확인된 배포본을 staging에 추출하고 `java.exe -version` 또는 동등한 검증으로 버전·아키텍처·종료 코드를 확인한 뒤 확정한다. 인스턴스용 실행 경로는 플랫폼에 맞게 설정한다. 기존 Java도 검증하고 Java 준비 실패는 가져오기 성공 조건을 만족하지 못한 것으로 처리한다.

프로세스 API는 `Stopped / RunningIdle / RunningGame / Unknown(error)`로 결과를 구분한다. 실행 파일 경로를 PowerShell 코드 문자열에 삽입하지 않는다. Windows 프로세스 API 또는 인자와 데이터를 분리한 조회로 executable identity와 PID를 확인한다. 게임 실행 또는 조회 실패면 준비 결과를 보관하고 확정을 보류한다. 정상 종료 실패에 대한 자동 강제 종료는 하지 않는다. 종료와 재실행 결과를 확인하고 원래 꺼져 있던 런처는 계속 꺼진 상태로 둔다.

검토한 대안: PowerShell 조회 실패를 false로 처리하면 안전 판단이 뒤집힌다. 새로운 Minecraft 버전마다 마지막 `else`를 바꾸는 방식은 snapshot 및 향후 버전에서 반복적으로 잘못된 Java를 지정하므로 metadata 기반으로 전환한다.

### D6. 작업 상태를 화면과 업데이트에서 공유한다 — R16–R19

이벤트는 `job_id`, `source_id`, `phase`, 단계별 `progress`, `terminal`, `error`, `retryable`을 포함한다. 프런트는 새 작업·비종료 이벤트를 받을 때 이전 숨김 타이머를 해제하고, 타이머 실행 시 작업 ID를 다시 확인한다. 이력 저장까지 끝난 경우에만 전체 완료로 표시한다. 재실행만 실패했다면 설치 완료 상태와 런처 오류를 따로 보여준다.

업데이트 검사·다운로드·설치에는 앱 전역의 단일 작업 상태와 lock을 둔다. 자동 검사와 수동 검사가 같은 경로를 사용한다. 수동 요청은 작업 ID 또는 실제 결과를 반환하고 UI는 상태 이벤트와 연결한다. 외부 오류를 확인 가능한 범주로 분류하며 근거가 없는 경우 미분류로 남긴다. 버전 비교는 updater의 의미론적 버전 처리를 사용한다.

안내 창은 기존 창이면 `show` 후 focus한다. 닫기 버튼에는 해당 창에 필요한 최소 권한 또는 Rust command를 제공한다. 전역 닫기 가로채기는 트레이 설정 창에 한정하고 안내 창의 hide/destroy 정책을 명확히 한다.

검토한 대안: 실패 횟수 임계값은 알림 빈도 제한에는 쓸 수 있으나 오류 원인 판별에는 쓸 수 없다. 백분율만 사용하는 화면은 후속 Java·이력 단계를 표현할 수 없어 명시적인 상태가 필요하다.

## Risks / Trade-offs

- [staging과 backup 용량 증가] → 준비 전 여유 공간 확인, 불충분하면 기존 설치를 유지하고 오류 표시.
- [Windows 파일 잠금·백신으로 rename 지연] → 제한된 재시도, journal 보존, 복구 완료 전 다음 작업 차단.
- [동기화 도중 같은 크기 콘텐츠 변경] → 원본 snapshot과 내용 fingerprint 확인.
- [이전 이력으로는 루트를 복원할 수 없음] → 현재 설정과 실제 파일·인스턴스를 대조하고 모호한 항목은 자동 이전 중단.
- [사용자 수정 파일과 팩 수정 파일 충돌] → 관리 파일의 이전 해시와 비교하고 보류·명시적 선택 제공.
- [원격 Java 메타데이터 접근 실패] → 검증된 캐시·알려진 fallback만 사용하고 알 수 없는 버전은 보류.
- [의도적으로 잘못된 기존 동작을 재현하는 테스트] → 현재 진단은 증거용으로 보존하고 제품 회귀 테스트에는 수정 후 기대 결과를 작성.

## Migration Plan

1. 공통 오류·식별·경로 정책과 테스트 경계를 먼저 추가한다. 기존 사용자 설정은 별도 fixture로 복제해 검증한다.
2. 이력 v2 이전 전에 v1 원본을 백업한다. 앱 시작 시 이전·복구 결과가 확정되기 전 자동 스캔을 시작하지 않는다.
3. 모호하지 않은 원본만 기존 인스턴스와 연결하고 나머지는 확인 대기로 둔다. 이전만으로 전체 재가져오기를 예약하지 않는다.
4. importer를 staging과 journal로 전환하고 제어 루프·UI가 새 상태를 소비하도록 함께 변경한다. 반쪽 계약으로 배포하지 않는다.
5. 격리된 Windows/Prism fixture에서 최초 설치, 세 형식 재가져오기, 게임 실행 중 보류, 설치 중단 복구, 업데이트 오류를 확인한다.
6. 새 버전 배포 전 v1/v2 양쪽 설정·이력 백업과 journal을 보존한다. 롤백은 앱·작업을 종료하고 미완료 설치를 먼저 복구한 뒤 원본 백업을 복원한다. 구버전 앱이 v2 이력을 읽고 빈 이력으로 재설치하지 않도록 롤백 절차에 자동 감시 중지를 포함한다.
