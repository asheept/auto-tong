# 반복 가져오기 및 알림 수정 계획

## 범위와 근거

대상은 Auto-Tong 0.3.0의 확인된 반복 경로다. 실제 사용자 오류 로그는 아직 없으므로 특정 팩의 최초 실패 원인을 추정해서 변경하지 않는다. 작업 브랜치는 fix/import-notification-loop이며 운영 앱 실행과 사용자 데이터 삭제를 수행하지 않는다. 후속 사용자 요청으로 검증한 수정본의 0.3.1 릴리스 배포를 진행한다.

## 구현 순서와 완료 기준

1. 복구 오류와 원본별 준비 오류 알림을 상태별로 관리한다. 동일한 오류가 지속되는 동안 알림은 한 번만 보내고, 문제가 해결된 뒤 새로 발생한 오류는 다시 알린다. 파일이 삭제돼도 남아 있는 복구 기록은 보존한다.
2. 다운로드/복사/압축 해제 전에 비파괴적으로 게임 및 런처 상태를 확인한다. 게임 실행이나 상태 조회 실패는 보류로 알리고 무거운 가져오기를 반복하지 않는다. 상태가 정상으로 돌아오면 자동 진행하고 설치 확정 직전 검사는 유지한다.
3. 임시 설치 폴더 생성 실패도 기존 실패 횟수 제한에 연결한다. 실패/취소 이력 저장 실패 시 저장되지 않은 성공을 만들지 않으며, 같은 콘텐츠를 자동으로 반복 처리하지 않도록 실행 중 보호 상태를 유지한다. 명시적 재시도 저장이 성공하면 보호 상태를 해제한다.
4. 최초 설치 journal 쓰기에 실패해 빈 복구 기록이 남는 경로를 제거한다. 기존 복구 기록과 백업의 보호 및 원자적 저장 동작은 유지한다.
5. 격리 회귀 테스트로 반복 스캔, 원본 삭제 후 복구 알림 중복, 정상화 후 재발, 게임 중 준비 작업 차단/종료 후 재개, 이력 저장 실패, 초기 journal 실패를 검증한다.
6. Rust 테스트·형식·clippy·Windows 빌드와 JavaScript 회귀 테스트·버전 검사를 실행하고 결과를 기록한다. 실제 사용자 PC의 증상 해결 및 배포와 로컬 검증을 구분한다.

## 상태

- 계획 작성, 원본 코드 점검 및 작업 브랜치 생성 완료.
- 구현·코드 리뷰·Rust 100개 및 JavaScript 8개 테스트·형식·clippy·Windows 개발 빌드 검증 완료. 자세한 근거는 verification-report.md에 기록했다. 실제 앱 배포는 수행하지 않았다.
## 배포 단계 추가

사용자의 후속 배포 요청에 따라 제품 버전을 0.3.1로 변경한다. 의존성과 검증된 제품 코드는 유지한다. 버전 일치 및 잠금 파일을 확인한 뒤 작업 브랜치 PR의 Windows CI 성공을 확인하고 master에 병합한다. 검증한 파일과 병합 커밋이 같은지 확인한 뒤 v0.3.1 태그로 Release workflow를 실행한다. 완료 기준은 정식 릴리스와 설치 파일 공개, GitHub SHA-256 및 앱 공개키로 업데이트 서명 검증, releases/latest/download/latest.json의 0.3.1 반영이다. 사용자 PC에 설치되었다고 추정하지 않는다.
